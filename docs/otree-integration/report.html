閉ループは動いた。 oTree → bridge → step-server → LLM → oTree の往復と、期間の「結果の書き戻し → 議論 → 次の決定」が実 LLM で最後まで通った。 oTree の記録と bridge の決定の食い違いは全ランで 0。

ただし、LLM の意思決定の妥当性に大きな問題が見つかった。 qwen3:4b は選択肢の文字 A を「協力的」と連想して選び、 gemma4:e4b は記号の見た目で選んで、相手が協力した後ほど裏切るという人間と逆の傾向を示した。議論も、ゲームの話にはほとんどならない。

結論: 現時点のデータは「言説が行動を変えた」証拠としては使えない。モデル比較、ラベルの扱い、話題誘導の強さの判断が次の課題。

3. システム構成

oTree 6（MIT）ゲームの正典。bot が各期に /decide、全ペア提出後に /round_complete
Flask bridge（AGPL）1期ぶんの決定を先取り。べき等、oTree の記録と突き合わせ、議論フェーズを実行
step-server（OASIS）議論0ラウンドで起動し、IPC で1ラウンドずつ進める。面接にフィードを差し込む
Ollamagemma4:e4b、8並列

1期の流れ

  1. bot が /decide → bridge は先取り済みの決定を返す（計算中なら待つ）
  2. 全ペアが提出 → /round_complete で oTree の記録を送る（これが正）
  3. bridge が裏で「結果を各自の投稿として注入 → 議論 k ラウンド → 次期の全員の決定を先取り」
  4. 次期の計算中の印は応答前に確保するので、議論が終わる前に決定が出ることはない

先取りが必要なのは、oTree の bot 実行が完全に直列だから。1体ずつ LLM を呼ぶと所要時間が人数倍になる。

6. 主な発見

  1. 協力の崩壊は「期間の議論」に伴って起きる（qwen3:4b）。 議論なし（ラン1）と冒頭投稿だけ（ラン4）は協力が続き、議論を挟んだラン2・3・5 はすべて崩れた。結果注入も冒頭投稿も必要条件ではなかった。
  2. その「協力」は文字 A への偏りだった。 意味を入れ替えると第1期に 8体中7体が A（今度は裏切り）を選び、理由は「相互の利益のために協力的な A」。理解テストは両条件で 8/8 正解で、読めているのに決定時は連想が勝つ。第2期以降はどちらも意味の上での相互裏切りに収束した。
  3. 議論の中身はゲームと無関係。 研究者ペルソナは研究紹介、一般人ペルソナは趣味の投稿ばかり。話題の毎期再掲で反応は 3件 → 7件に増えたが、全約80件の一部。結果投稿への反応は 0。エージェントは自分の投稿を自分のフィードで読んでいた。
  4. gemma4:e4b と記号ラベルでは別の偏り。 「◇ is where the magic happens」のように記号の見た目とペルソナの作風で選ぶ。協力率は 0〜0.6 と低く、相手が協力した後ほど裏切る逆向きの相互主義。ラベルをエージェント単位にすると第1期の協力率は 0.12 → 0.38。
  5. 信念調査は行動と一致しない（qwen3:4b）。 全員が裏切り合った直後でも「信頼したほうがよい」が 7.0 に上がった。gemma4:e4b では下がり、行動と同じ向きに動いた。

7. 見つかった不具合と対処（抜粋）

#現象対処
6初期投稿が最初のラウンドのログに二重記録（既存の不具合）初期投稿後の DB 位置から数え始める
9, 18注入投稿や面接が「自発的な行動」として議論ログに混入注入・面接の直後に DB を読み進める
19既存の面接結果の読み出しは、失敗時に前回の回答を返しうるゲーム用の面接では今回の分だけ読む
20意思決定時のフィードが空（推薦テーブルが古い）面接前に推薦テーブルを更新
22, 23リローダーで bridge が再起動し、黙ってランダム方策で答え続けたFLASK_DEBUG=false 必須、未設定セッションは 409 で拒否
26止めたはずの旧 step-server が次のランのコマンドを横取りpid ファイルで二重起動を拒否
31模擬時計が進むと議論が空回り時刻による活性化を無視、最低活性人数を保証
33ラン中のテンプレート編集で途中からプロンプトが変わる自動再読み込みを無効化
39, 40文字 A への偏り記号ラベル、ランダム化、選択肢ごとの利得の言い直し

限界

  • すべて 8体・各条件1ラン。条件間の差について因果は主張できない
  • 記号ラベルをセッション単位でランダムにすると、1セッション内では全員が同じ偏りを受ける
  • 意思決定時のフィードは2件程度に固定されていて、議論の窓が狭い
  • oTree の bot 実行は直列なので、並行アクセス時の安全性は未検証
  • OLLAMA_NUM_PARALLEL=8 は OS の再起動で消える

8. 次に判断が必要なこと

  1. モデル比較 — gemma4:e4b の逆向きの相互主義がモデル固有かを、gemma4:12b などで確かめるか
  2. 話題誘導の強さ — 議論ラウンド中の行動プロンプトに話題を入れるか（ゲームの話にはなるが誘導が強くなる）
  3. ラベルのランダム化の単位 — セッション単位（現在の既定）か、エージェント単位か
  4. 本番規模（48体）の実行 — 現構成で、議論ありなら1ランあたり1〜1.5時間程度の見込み
