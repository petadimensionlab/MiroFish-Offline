## 1. 概要

### 目的

行動実験フレームワーク **oTree** の経済ゲームを、**MiroFish-Offline** の LLM エージェントにプレイさせる。
ゲームの期と期の間に、エージェントが模擬 SNS で議論する「議論フェーズ」を挟み、
**言説 → 行動 → 言説** の双方向フィードバック（閉ループ）を作る。

### 結論（要約）

1. **閉ループは動いた。** oTree の反復囚人のジレンマ → bridge → MiroFish の step-server → LLM 面接 → oTree、
   の往復と、期間の「結果の書き戻し → 議論 → 次の決定」が、実 LLM で最後まで通った（計9ラン、欠測と食い違いはほぼゼロ）。
2. **計画の Phase 0〜4 は完了、Phase 5 は着手。** 実験条件を切り替える仕組み（議論・結果注入・話題投稿・ラベル・信念調査・理解テストなど）はそろった。
3. **ただし、LLM の意思決定の妥当性に大きな問題が見つかった。**
   - qwen3:4b は選択肢の**文字 A を「協力的な選択」と連想して選ぶ**。利得表の意味を入れ替えても A を選ぶ（第1期 8体中7体）。
     利得表の理解テストには全員正解しているので、「読めていないのではなく、決定時に連想が優先している」。
   - gemma4:e4b に記号ラベルを使うと、今度は**記号の見た目**（「◇ は魔法っぽい」）で選び、協力率は低く、
     **相手が協力した後ほど裏切る逆向きの相互主義**を示した。人間の典型とは逆。
4. **議論は起きるが、ゲームの話になりにくい。** エージェントは自分のペルソナの関心事（研究、庭仕事、写真など）を投稿し続ける。
   話題の毎期再掲で反応はやや増えたが、全体の一部にとどまる。
5. 以上から、**現時点のデータは「言説が行動を変えた」証拠としては使えない。** モデル比較、ラベルの扱い、話題誘導の強さの判断が次の課題。

## 3. システム構成

```
┌──────────────────────────────┐   HTTP    ┌──────────────────────────────────┐  file IPC  ┌──────────────────────────────┐
│ oTree 6.0.15（MIT、別リポジトリ）│ ───────▶ │ MiroFish Flask bridge（AGPL）       │ ─────────▶ │ step-server（OASIS）            │
│  pd_debate: 2人固定ペア×10期     │           │  /api/experiment                   │            │  run_experiment_env.py        │
│  bot → /decide                │ ◀─────── │  先取り・べき等・突き合わせ           │ ◀───────── │  run_rounds / inject_post /   │
│  DebateBarrier → /round_complete│           │  議論フェーズの実行                 │            │  game_interview / get_state   │
└──────────────────────────────┘           └──────────────────────────────────┘            └──────────────────────────────┘
                                                                                                   │ Ollama（gemma4:e4b, 8並列）
```

- **oTree** がゲームの正典（利得計算・記録）。bot は各期に bridge へ決定を問い合わせる
- **bridge** は1期ぶんの全員の決定を、前期のバリア到達時点で**先取り**する（oTree の bot 実行は完全に直列なので、1体ずつ LLM を呼ぶと時間が人数倍になる）
- **step-server** は OASIS の環境を議論ラウンド0回で起動し、IPC で議論を1ラウンドずつ進める。面接時は各エージェントが今見ているフィードをプロンプトに差し込む

### 1期の流れ

1. bot が `/decide` → bridge は先取り済みの決定を返す（まだ計算中なら待つ）
2. 全ペアが提出 → `DebateBarrier` → `/round_complete`（oTree が記録した結果を送る。これが正）
3. bridge が裏で: ① 結果を各エージェントの投稿として注入 → ② 議論 k ラウンド → ③ 次期の全員の決定を先取り
4. 次期の in-flight（計算中の印）は `/round_complete` が返る前に確保するので、議論が終わる前に決定が出ることはない

## 4. 実装の詳細

### 4.1 R1: ランナーのリファクタ

既存の `run_twitter_simulation` / `run_reddit_simulation` はブートストラップと全ラウンドのループを1関数に抱えていて、途中で止めて外から進めることができなかった。
3つの関数に分け、既存ランナーはそれを呼ぶだけにした。

| 関数 | 役割 |
|---|---|
| `setup_platform_env()` | モデル・プロフィール・エージェントグラフ・DB・OASIS 環境の起動（ラウンド0回） |
| `publish_initial_posts()` | 第0ラウンドの初期投稿。初期投稿後の DB の位置を返す |
| `step_round()` | 1ラウンドぶん（活性化するエージェントの選択 → `env.step` → DB 差分 → ログ） |

### 4.2 step-server（`run_experiment_env.py`）

起動時は議論ラウンドを実行せず、IPC コマンドを待つ。

| コマンド | 内容 |
|---|---|
| `run_rounds` | 議論を k ラウンド進める。参加候補をゲーム参加者に限定、時刻による活性化の無視、最低活性人数の保証、が指定できる |
| `inject_post` | 複数の投稿を1回の `env.step` で公開。注入投稿は `injected: true` 付きで記録 |
| `game_interview` | 意思決定用の一括面接。プロンプト中の `{{FEED}}` を各エージェントの今のフィードに置き換え、見たフィードも返す |
| `get_state` | ラウンド数などの状態 |
| 既存の `interview` / `batch_interview` / `close_env` | そのまま利用 |

pid ファイルで二重起動を拒否する（止めたはずの旧プロセスがコマンドを横取りした事故への対策）。

### 4.3 bridge（`experiment_bridge.py`）

- **方策**: `random` / `allc` / `alld` / `tft`（ダミー）と `llm`
- **べき等性**: 同じ（セッション, 期, エージェント）には同じ決定を返す。計算中に同じ要求が来たら、二重に計算せず先行の結果を待つ
- **突き合わせ**: `/round_complete` で oTree が実際に記録した選択を受け取り、bridge の決定と食い違えば記録する（タイムアウトでデフォルト値が使われた場合など）
- **議論フェーズ**: 冒頭の話題投稿、結果の注入（各自の投稿 / 要約1件 / なし）、議論ラウンド、話題の毎期再掲
- **未設定のセッションを拒否**: bridge が再起動して状態を失った後に、黙ってランダム方策で答え続けた事故への対策
- **ログ**: `<sim_dir>/game/<session>/` に `bridge_log.jsonl`、`llm_answers.jsonl`（プロンプト・見たフィード・生の応答）、`beliefs.jsonl`、`comprehension.jsonl`

### 4.4 oTree アプリ（`pd_debate`）

- 2人固定ペア×10期。利得は R=30（両者協力）、T=50（裏切り成功）、S=0（裏切られ）、P=10（両者裏切り）
- oTree の内部値は常に A=協力・B=裏切り。エージェントに見せるラベルは bridge が決める
- `creating_session` でラベル付け（`agent_<id>`）とペア表の送信、`DebateBarrier` で全ペア提出後に1回だけ `/round_complete`
- bridge 呼び出しは例外を投げない（未捕捉例外は oTree のラン全体を落とすため）。失敗時はデフォルト値＋欠測フラグ
- CSV（`pd_debate_custom.csv`）: 1行＝1体×1期、選択・相手の選択・利得・決定の出所・欠測・理由 など16列

### 4.5 意思決定プロンプトと解釈

- 利得は**選択肢ごとに言い直す**（「△ を選んだ場合: 相手が △ なら…、□ なら…」）
- ラベルは `letters`（A/B）か `symbols`（△□○◇）。対応づけと並び順を**セッション単位またはエージェント単位でランダム**に決める
- これまでの履歴、今見ているフィード、JSON で答える指示を含む
- 解釈は `<think>` やコードフェンスを除いて JSON を読み、読めなければ厳格版で1回だけ再質問、それでも駄目ならデフォルト値＋欠測

### 4.6 測定

| 測定 | 内容 |
|---|---|
| 理解テスト | 第1期の前に「△ を選び相手が □ なら何点？」など2問 |
| 信念調査 | 「同じ相手なら信頼したほうがよい」への同意（7件法）をゲームの前後に |
| 分析 | `analyze_session.py`: 期ごとの協力率、相互協力・相互裏切り・分かれの数、条件付き協力、LLM の解釈状況、議論の行動数、話題への反応 |

### 4.7 一般人ペルソナの生成（`make_general_sim.py`）

年齢・性別・国・職業・性格・関心を seed 固定で割り当て、プロフィール文だけ LLM が書く。ゲームの主題（信頼・協力・戦略・経済）はプロフィールから除外。
48体を約3分半で生成（`sim_general_s1_n48`）。

### 5.6 主な発見

**(1) 協力の崩壊は「期間の議論」に伴って起きる（qwen3:4b、ラン1〜5）。**
議論なし（ラン1）と冒頭投稿だけ（ラン4）は協力が続き、議論を挟んだラン（2, 3, 5）はすべて崩れた。
結果注入も冒頭投稿も必要条件ではなかった（ラン5 は注入も冒頭投稿もなしで 0.00 まで崩壊）。

**(2) ただし、その「協力」は文字 A への偏りだった（ラン5 と 6）。**
利得表の意味を入れ替える（A＝裏切り）と、第1期に 8体中7体が A を選んだ。理由は「相互の利益のために協力的な A」。
理解テストは入れ替えの有無どちらでも 8/8 正解。**読めているのに、決定時には「A＝協力的」の連想が勝つ。**
第2期以降は履歴に反応し、どちらの条件も意味の上での相互裏切りに収束した。
解釈としては、「議論なしでは『両者 A で30点』が安定するが、議論の語彙（proactive、outperform など）がごく一部を B に揺らすと、相互主義で相互裏切りへ崩れる」。

**(3) 議論の中身はゲームと無関係。**
研究者ペルソナでは投稿はほぼすべて研究紹介、一般人ペルソナでも趣味の投稿（庭仕事、古着、夕焼け）。
冒頭の話題投稿への反応は 3件、話題を毎期再掲すると 7件に増えた（全 約80件中）。注入した結果投稿への反応は0。
**エージェントは自分の投稿を自分のフィードで読んでいる**点も、記録したフィードから分かった。

**(4) gemma4:e4b と記号ラベルでは別の偏りが出る（ラン7〜9）。**
文字 A の偏りは消えたが、「◇ is where the magic happens」のように**記号の見た目とペルソナの作風**で選ぶ。
協力率は全期 0〜0.6 と低く、**相手が協力した後ほど裏切る逆向きの相互主義**（0.06 / 0.29、0.14 / 0.35）。
ラベルをエージェント単位でランダムにすると第1期の協力率は 0.12 → 0.38 に上がった。理解テストは毎回 8/8。

**(5) 信念調査は行動と一致しない（qwen3:4b）。**
全員が裏切り合った直後でも「信頼したほうがよい」が 6.9〜7.0 に上がった。gemma4:e4b では 4.7 → 3.4 などと下がり、行動と同じ向きに動いた。

| 6 | 初期投稿が最初のラウンドのログに二重記録（既存ランナーの不具合） | 初期投稿後の DB 位置から数え始める |

| 20 | フィードが空（推薦テーブルが次の step まで更新されない） | 面接前に推薦テーブルを更新 |

| 26 | 止めたはずの旧 step-server が次のランのコマンドを横取り | pid ファイルで二重起動を拒否 |
| 31 | 模擬時計が進むと活動時間帯の外に出て、議論が空回り | 時刻による活性化を無視、最低活性人数を保証 |
| 33 | ラン中にテンプレートを編集すると、途中からプロンプトが変わる | テンプレートの自動再読み込みを無効化 |
| 39, 40 | 文字 A への偏り | 記号ラベル、ランダム化、選択肢ごとの利得の言い直し |

## 7. 限界

- すべて **8体・各条件1ラン**。条件間の差について因果は主張できない
- 記号ラベルをセッション単位でランダムにすると、1セッション内では全員が同じ偏りを受ける。打ち消しには多数のセッションが要る
- OASIS の Twitter 環境は意思決定時のフィードが2件程度に固定されていて、議論の窓が狭い
- oTree の bot 実行は直列なので、並行アクセス時の安全性は未検証
- `OLLAMA_NUM_PARALLEL=8` は OS の再起動で消える

## 8. 次に判断が必要なこと

1. **モデル比較**: gemma4:e4b の逆向きの相互主義がモデル固有かを、gemma4:12b などで確かめるか
2. **話題誘導の強さ**: 議論ラウンド中の行動プロンプトに話題を入れるか（ゲームの話にはなるが、誘導が強くなる）
3. **ラベルのランダム化の単位**: セッション単位（現在の既定）か、エージェント単位か
4. **本番規模（48体）の実行**: 現構成で、議論ありなら1ランあたり1〜1.5時間程度の見込み

## 付録 B. 用語

| 用語 | 意味 |
|---|---|
| 反復囚人のジレンマ | 同じ相手と何度も「協力か裏切りか」を同時に選ぶゲーム。1回ごとには裏切りが得だが、互いに協力し続けると両者の得が大きい |

| 結果注入 | 各期の結果を、エージェント自身の投稿として模擬 SNS に書き戻すこと |
| 理解テスト | 利得表を正しく読めているかを確かめる事前の質問 |
